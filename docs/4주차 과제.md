# 4주차 과제

# 📄 시작하기에 앞서

3주차에는 Waggle API에 인증과 인가를 붙였습니다. 이제 요청자가 누구인지 확인하고, 역할과 가입 상태, 담당하거나 수강 중인 세미나에 따라 요청을 허용하거나 거절할 수 있습니다.

그런데 요청을 하나씩 보낼 때 정상적으로 동작하는 코드도, 여러 요청이 동시에 들어오면 정원을 초과하거나 같은 신청을 두 번 저장할 수 있습니다. 여러 데이터를 함께 고치다가 중간에 실패하면 일부만 반영될 수도 있습니다.

이번 주에는 **트랜잭션과 동시성 제어**로 데이터 정합성을 지키고, **자동화된 테스트**로 이를 확인합니다. 남아 있는 출석·과제 기록과 대시보드 기능도 구현하여, 다음 주에 배포할 Waggle 서비스를 완성합니다.

- 기존 수강 신청과 취소가 동시에 실행되어도 정원과 신청 정보가 올바르게 유지되어야 합니다.
- 운영진이 수강생의 잔여 Grace Day, 탈락 여부, 출석과 과제 상태를 관리할 수 있어야 합니다.
- 여러 수강생의 기록을 한 번에 수정할 때는 전부 반영되거나, 실패하면 전부 반영되지 않아야 합니다.
- 팀이 직접 동시성 테스트와 롤백 테스트를 작성하고 설계 근거를 설명해야 합니다.

## 0. 4주차 자료 받기

### 자료 받기

2·3주차와 같은 방법으로, 진행 중인 작업을 커밋한 뒤 운영진이 공지한 원본 업데이트를 받아옵니다.

```bash
git switch main
git pull --ff-only origin main
git fetch upstream
git merge upstream/main
```

충돌이 발생하면 기존 팀 구현과 새 자료의 변경 의도를 확인하여 해결합니다. 아래 파일들을 함께 확인해주세요.

| 경로 | 확인할 내용 |
| --- | --- |
| `docs/4주차 과제.md` | 이번 주 구현 요구사항과 API 명세 |
| `docs/서비스 요구사항.md` | 서비스 전체의 도메인 규칙 |
| `src/test/.../support/ApiIntegrationTest.kt` | MockMvc, 테스트용 MySQL, 사용자·세미나 생성 도우미 |
| `src/test/.../*Test.kt` | 운영진이 제공하는 공개 테스트 |
| `build.gradle.kts` | 채점 환경에서 사용하는 의존성 |

테스트를 실행할 때는 Docker가 켜져 있어야 합니다. 테스트용 MySQL은 Testcontainers가 별도로 띄우므로, 개발용 DB를 비우거나 `compose.yaml`의 DB를 테스트용으로 재사용할 필요는 없습니다.

### 스키마 변경

테이블과 컬럼 이름, 테이블을 나누는 방법은 팀이 정합니다. 필요한 제약조건이나 컬럼, 기록용 테이블이 없다면 **다음 버전 번호의 Flyway Migration**을 새로 추가하세요.

예를 들어 마지막 파일이 `V2__seed_admin.sql`이면 `V3__add_session_records.sql`처럼 작성할 수 있습니다. 버전 번호는 팀의 기존 Migration에 맞춥니다.

- 이미 적용한 Migration을 수정하거나 삭제하지 않습니다.
- 기존 사용자, 세미나, 수강 신청 데이터를 유지하면서 변경해야 합니다.
- 빈 DB에 전체 Migration을 적용하는 경우와, 기존 DB에 새 Migration을 추가 적용하는 경우를 모두 확인합니다.
- `enrolled_count`처럼 별도 집계 컬럼을 추가한다면 기존 수강 신청을 기준으로 초기값을 채우고, 이후 신청·취소와 함께 일관되게 관리합니다.

### 의존성

기존 Spring Data JDBC, MySQL, Flyway, Testcontainers와 Java의 동시성 도구를 사용할 수 있습니다. 동시성 제어를 위해 특정 라이브러리를 새로 추가해야 하는 것은 아닙니다.

채점 서버는 `build.gradle.kts`를 운영진 원본의 것으로 사용합니다. 필요한 의존성이 있다면 운영진에게 알려주세요. 팀에서 임의로 추가한 의존성은 채점 환경에 반영되지 않습니다.

## 1. 수강 신청과 취소의 동시성 보장

### 기존 API 계약 유지

다음 두 엔드포인트의 요청과 성공 응답은 3주차와 같습니다. 수강 신청자는 요청 본문이 아니라 토큰으로 식별합니다.

| 기능 | 메서드와 경로 | 성공 |
| --- | --- | --- |
| 수강 신청 | `POST /seminars/{seminarId}/enrollments` | `201 Created` |
| 본인 수강 취소 | `DELETE /seminars/{seminarId}/enrollments/me` | `204 No Content` |

- 가입이 승인된(`APPROVED`) 루키만 자신의 신청과 취소를 할 수 있습니다. 3주차의 인증·인가 규칙을 그대로 적용합니다.
- 수강 신청은 신청 기간 안이고 정원이 남아 있을 때만 가능합니다. 이미 신청했거나 신청할 수 없는 상태라면 `409`입니다.
- 취소는 `applyStartAt ≤ 현재 < applyEndAt`일 때 가능합니다. 기간 밖이면 `409`입니다.
- 정원 도달로 세미나의 `status`가 `CLOSED`여도 신청 기간 안이라면 취소할 수 있습니다.
- 없는 세미나에 신청하거나, 해당 세미나에 자신의 수강 신청이 없는데 취소하면 `404`입니다.

### 정원 초과 방지

정원이 `N`명인 세미나에는 동시에 요청이 들어와도 최대 `N`개의 수강 신청만 존재해야 합니다.

단순히 정원을 넘지 않는 것만으로는 충분하지 않습니다. 신청 기간 안인 빈 세미나에 서로 다른 승인 루키 `M`명이 한 번씩 동시에 신청하면, 취소나 다른 변경이 없는 상황에서 다음 결과를 만족해야 합니다.

```text
신청 성공 수 = min(N, M)
정원 마감으로 실패한 수 = M - min(N, M)
최종 수강 신청 수 = 신청 성공 수
```

예를 들어 정원 30명에 100명이 신청하면 **30건은 `201`, 70건은 `409`**여야 합니다. 정원이 남았는데 락 충돌을 그대로 반환하여 일부 사용자만 성공하는 구현은 요구사항을 만족하지 않습니다. 재시도가 필요한 전략을 선택했다면 재시도까지 포함해 처리하세요.

동시에 요청한 사용자 중 누가 성공하는지는 정하지 않습니다. 테스트는 스레드를 생성하거나 작업을 제출한 순서와 성공 순서가 같다고 가정하지 않습니다.

### 중복 신청과 중복 취소 방지

한 루키가 같은 세미나에 동시에 여러 번 신청해도 수강 신청은 하나만 생성되어야 합니다.

| 상황 | 기대 결과 |
| --- | --- |
| 신청 기간 안이고 자리가 있는 세미나에, 아직 신청하지 않은 한 루키가 20회 동시 신청 | `201` 1건, `409` 19건, 수강 신청 1개 |
| 신청 기간 안에, 한 루키가 자신의 기존 신청에 대해 10회 동시 취소 | `204` 1건, `404` 9건, 해당 수강 신청 0개 |

신청 실패가 남은 자리를 소비해서는 안 되며, 취소 실패가 인원을 추가로 줄여서도 안 됩니다. 신청을 취소한 뒤에는 신청 기간 안에서 다시 신청할 수 있어야 합니다.

### 신청과 취소가 섞이는 경우

기존 수강생의 취소와 새로운 루키의 신청이 동시에 실행되어도, 모든 요청이 끝난 뒤에는 다음을 만족해야 합니다.

```text
최종 인원 = 초기 인원 + 신청 성공 수 - 취소 성공 수
0 ≤ 최종 인원 ≤ 정원
```

신규 신청이 취소보다 먼저 처리되면 자리가 없어 실패할 수 있습니다. 따라서 이 경우에는 최종 인원이 무조건 정원과 같아야 하는 것은 아닙니다. 이후 빈자리에 새 사용자가 신청하면 정상적으로 자리를 채울 수 있어야 합니다.

세미나 단건·목록 조회의 `enrolledCount`와 `status`, 내 수강 목록, 대시보드가 보여 주는 정보도 실제 수강 신청과 일치해야 합니다. 이 비교는 동시 작업이 모두 끝난 뒤 수행합니다.

### 취소 시 관련 기록 정리

이번 주에는 수강 신청에 연결된 출석·과제 기록도 생깁니다. 취소가 성공하면 **해당 수강 신청과 그 신청에 연결된 출석·과제 기록을 함께 제거**해야 합니다. 다른 수강생의 기록이나 세미나의 회차는 유지합니다.

정원 집계 값을 따로 저장한다면 인원 감소도 같은 작업에 포함합니다. 어느 단계에서든 실패하면 앞선 변경을 포함해 전체를 되돌려야 합니다.

취소 후 다시 신청하면 잔여 Grace Day는 세미나의 `totalGraceDays`, 탈락 여부는 `false`로 시작합니다. 이전 신청의 출석·과제 기록은 복원하지 않습니다.

### 구현 방식

비관적 락, 낙관적 락과 재시도, 조건부 Atomic Update 등 어떤 방식을 사용할지는 각 팀이 정합니다.

- 애플리케이션의 중복 조회만으로 동시 중복 저장까지 막을 수 있는지 생각해 보세요. DB의 `UNIQUE` 제약조건도 함께 고려합니다.
- 비관적 락을 사용한다면 락 획득부터 검사와 저장이 끝날 때까지 트랜잭션 경계가 유지되어야 합니다.
- 별도 인원 컬럼을 사용한다면 신청 실패, 중복 요청, 취소 실패와 롤백까지 고려해야 합니다.
- 예상한 업무 충돌은 정해진 상태 코드로 처리하고, 예상하지 못한 DB 오류를 모두 `409`로 바꾸어 숨기지 않습니다.

선택한 방식과 적용 범위, 다른 방식 대신 이를 선택한 이유는 [설계 문서](#design-document)에 설명해주세요.

## 2. 운영 기능과 권한

### 운영 정보의 의미

운영진은 수강 신청에 연결된 정보를 관리합니다. 같은 루키라도 세미나마다 잔여 Grace Day와 탈락 여부가 다를 수 있습니다.

| 항목 | 초기값 | 규칙 |
| --- | --- | --- |
| 잔여 Grace Day | 세미나의 `totalGraceDays` | 정수. `0` 이상, 해당 세미나의 `totalGraceDays` 이하 |
| 탈락 여부 | `false` | 운영진이 직접 수정하는 표시용 값 |
| 회차별 출석 | `null` | `PRESENT`, `ABSENT` 또는 미기록 |
| 회차별 과제 상태 | `null` | `PASSED`, `SUBMITTED_BUT_FAILED`, `NOT_SUBMITTED` 또는 미기록 |

- 미기록은 결석이나 미제출이 아닙니다. 응답에서 `null`로 표현합니다.
- Grace Day는 운영진이 직접 조정합니다. 과제 상태나 날짜에 따라 자동 차감하지 않습니다.
- `dropped=true`여도 수강 신청을 삭제하지 않습니다. 정원에 포함되고, 내 수강 목록과 대시보드에도 계속 나옵니다.
- 탈락 표시는 조회 권한이나 출석·과제 기록 수정 가능 여부에 영향을 주지 않습니다.
- 신청 기간이 끝난 뒤에도 운영 정보와 출석·과제 기록은 수정할 수 있습니다. 신청·취소에 적용하는 기간 제한과 구분합니다.

### 권한 표

새 엔드포인트는 모두 로그인이 필요합니다. 와장과 운영진, 루키의 역할 및 가입 상태는 3주차와 같습니다.

| 기능 | 와장 | 담당 운영진 | 다른 세미나 운영진 | 이 세미나 수강 중인 루키 | 미수강 루키 |
| --- | --- | --- | --- | --- | --- |
| 대시보드 조회 | 가능 | 가능 | 불가 | 가능 | 불가 |
| 수강 정보 수정 | 가능 | 가능 | 불가 | 불가 | 불가 |
| 출석·과제 일괄 수정 | 가능 | 가능 | 불가 | 불가 | 불가 |

- 운영진과 루키는 가입이 승인된(`APPROVED`) 경우에만 위 권한을 가집니다. `PENDING`·`REJECTED`이면 `403`입니다.
- 수강 중인 루키는 **자신뿐 아니라 같은 세미나의 다른 수강생 현황도 조회**할 수 있습니다. 대시보드를 수정할 수는 없습니다.
- 탈락 표시가 되어 있어도 수강 신청이 남아 있다면 수강 중인 루키입니다. 수강을 취소하면 조회 권한을 잃습니다.
- 인증 실패는 다른 검사보다 먼저 판단하여 `401`을 반환합니다. 인증 규칙은 3주차와 같습니다.
- 인가 실패(`403`)와 다른 실패(`400`·`404`·`409`)가 동시에 해당하는 요청은 채점하지 않습니다. 서로 다른 요청 오류가 동시에 해당할 때의 우선순위도 채점하지 않습니다.

### 에러 응답과 부분 수정

에러 응답은 기존 `ApiErrorResponse` 형식을 사용합니다. `code`와 `message` 내용은 팀이 정하며, 오류 응답의 채점은 상태 코드를 기준으로 합니다.

```json
{
  "code": "INVALID_REQUEST",
  "message": "요청값이 올바르지 않습니다.",
  "fieldErrors": []
}
```

새 `PATCH` 엔드포인트도 **보낸 항목만 수정**합니다. 명세에 없는 프로퍼티는 무시합니다. 다만 알 수 없는 프로퍼티만 보내거나, 필수 식별자 외에 수정할 항목이 전혀 없는 요청은 아래 명세에 따라 `400`입니다.

## 3. 엔드포인트

이번 주에는 기존 엔드포인트의 요청·응답을 유지하고 다음 세 엔드포인트를 추가합니다. 기존 기능의 변경 사항은 [수강 신청과 취소](#1-수강-신청과-취소의-동시성-보장)에 적힌 동시성 보장과 취소 시 기록 정리입니다.

| 기능 | 메서드와 경로 |
| --- | --- |
| [대시보드 조회](#dashboard) | `GET /seminars/{seminarId}/dashboard` |
| [수강 정보 수정](#enrollment-update) | `PATCH /seminars/{seminarId}/enrollments/{enrollmentId}` |
| [출석·과제 일괄 수정](#records-update) | `PATCH /sessions/{sessionId}/records` |

### `GET /seminars/{seminarId}/dashboard`

세미나의 회차와 수강생별 운영 현황을 조회합니다. **행은 수강생, 열은 회차**인 화면을 만들기 위한 API입니다. 수강생 목록은 페이지 단위로 응답합니다.

와장, 담당 운영진, 해당 세미나를 수강 중인 루키가 조회할 수 있습니다. 다른 세미나 운영진이나 미수강 루키가 요청하면 `403`입니다.

**요청** — 쿼리 파라미터

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `page` | integer | | 0부터 시작하는 페이지 번호. 기본값 0, 0 이상 |
| `size` | integer | | 한 페이지의 수강생 수. 기본값 20, 1 이상 100 이하 |

**응답** — `200 OK`

```json
{
  "seminarId": 1,
  "sessions": [
    {
      "id": 7,
      "round": 1,
      "title": "트랜잭션과 동시성",
      "startsAt": "2026-10-20T19:00:00+09:00",
      "assignmentTitle": "Waggle 데이터 정합성 보장"
    },
    {
      "id": 8,
      "round": 2,
      "title": "배포",
      "startsAt": "2026-11-03T19:00:00+09:00",
      "assignmentTitle": "Waggle 서버 배포"
    }
  ],
  "content": [
    {
      "id": 10,
      "user": {
        "id": 5,
        "email": "waffle@snu.ac.kr",
        "name": "김와플",
        "githubUsername": "waffle-kim"
      },
      "graceDaysRemaining": 2,
      "dropped": false,
      "createdAt": "2026-09-15T21:02:00+09:00",
      "records": [
        {
          "sessionId": 7,
          "attendance": "PRESENT",
          "assignmentStatus": "PASSED"
        },
        {
          "sessionId": 8,
          "attendance": null,
          "assignmentStatus": null
        }
      ]
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

| 항목 | 타입 | 설명 |
| --- | --- | --- |
| `seminarId` | integer | 조회한 세미나의 ID |
| `sessions` | array | 이 세미나의 전체 회차 목록. 페이지와 관계없이 동일한 범위 |
| `sessions[].id` | integer | 회차의 ID |
| `sessions[].round` | integer | 정렬된 순서에서 계산한 회차 번호. 1부터 시작 |
| `sessions[].title`, `startsAt`, `assignmentTitle` | string | 기존 회차 조회의 같은 이름 항목과 같은 의미 |
| `content` | array | 이번 페이지의 수강생 현황 |
| `content[].id` | integer | **수강 신청(enrollment)의 ID**. 사용자 ID와 구분합니다 |
| `content[].user` | object | 해당 루키의 `id`, `email`, `name`, `githubUsername` |
| `content[].graceDaysRemaining` | integer | 해당 세미나에서의 잔여 Grace Day |
| `content[].dropped` | boolean | 해당 세미나에서의 탈락 표시 |
| `content[].createdAt` | string | 수강 신청 일시. ISO-8601 |
| `content[].records` | array | 이 수강생의 회차별 출석·과제 현황 |
| `records[].sessionId` | integer | 기록이 가리키는 회차의 ID |
| `records[].attendance` | string \| null | `PRESENT`, `ABSENT` 또는 `null` |
| `records[].assignmentStatus` | string \| null | `PASSED`, `SUBMITTED_BUT_FAILED`, `NOT_SUBMITTED` 또는 `null` |
| `page`, `size` | integer | 요청한 페이지 번호와 크기 |
| `totalElements` | integer | 해당 세미나의 전체 수강생 수. 탈락 표시된 수강생도 포함 |
| `totalPages` | integer | 전체 페이지 수. 수강생이 없으면 0 |

**목록과 미기록 처리**

- `sessions`는 `startsAt` 오름차순, 같은 시각이면 회차 ID 오름차순입니다. `round`는 이 순서대로 계산하며 기존 회차 조회 결과와 같아야 합니다.
- `content`는 수강 신청 ID 오름차순입니다. 페이지네이션은 `content`에만 적용합니다.
- 각 수강생의 `records`에는 `sessions`의 모든 회차가 같은 순서로 정확히 한 번씩 나옵니다. 기록이 없는 회차도 생략하지 않습니다.
- 기록하지 않은 출석과 과제 상태는 각각 `null`입니다. 두 프로퍼티를 생략하지 않습니다.
- 회차가 없으면 `sessions`와 각 행의 `records`는 빈 배열입니다.
- 수강생이 없거나 범위를 벗어난 페이지이면 `content`는 빈 배열입니다. `sessions`와 전체 수강생 기준의 `totalElements`, `totalPages`는 그대로 응답합니다.
- 회차의 `startsAt`을 수정하면 대시보드의 회차 순서와 `round`도 달라질 수 있습니다. 기존 기록은 표시 번호가 아니라 **회차 ID**에 연결되어야 합니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `page`가 음수이거나 `size`가 1 미만 또는 100 초과 | 400 |
| `page` 또는 `size`가 정수가 아님 | 400 |
| 없는 세미나 | 404 |

<a id="enrollment-update"></a>

### `PATCH /seminars/{seminarId}/enrollments/{enrollmentId}`

수강생의 잔여 Grace Day와 탈락 여부를 수정합니다. 경로의 `enrollmentId`는 사용자 ID가 아니라 수강 신청 ID입니다.

와장과 해당 세미나의 담당 운영진만 수정할 수 있습니다. 다른 세미나 운영진이나 루키가 요청하면 `403`입니다.

**요청**

```json
{
  "graceDaysRemaining": 2,
  "dropped": true
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `graceDaysRemaining` | integer | | 0 이상, 해당 세미나의 `totalGraceDays` 이하. `null` 불가 |
| `dropped` | boolean | | `true` 또는 `false`. `null` 불가 |

- 두 항목 중 적어도 하나를 보내야 합니다. 보낸 항목만 수정하고, 생략한 항목은 유지합니다.
- 두 항목을 함께 보냈을 때 하나라도 잘못되면 **어느 항목도 수정하지 않습니다.**
- 같은 값을 다시 보내는 것은 정상 요청입니다.
- 수강 신청의 ID와 신청 일시는 변경하지 않습니다.
- 잔여 Grace Day와 탈락 여부는 이후 대시보드와 기존 `GET /users/me/enrollments`에도 반영되어야 합니다.
- 이 요청은 수강 신청을 취소하거나 출석·과제 기록을 변경하지 않습니다.

**응답** — `200 OK`

```json
{
  "id": 10,
  "graceDaysRemaining": 2,
  "dropped": true,
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 수정할 항목이 없음 | 400 |
| `graceDaysRemaining`이 정수가 아니거나 허용 범위 밖임 | 400 |
| `dropped`가 boolean이 아님 | 400 |
| 두 항목 중 하나에 명시적으로 `null`을 보냄 | 400 |
| 없는 세미나 또는 없는 수강 신청 | 404 |
| 수강 신청이 경로의 세미나에 속하지 않음 | 404 |

<a id="records-update"></a>

### `PATCH /sessions/{sessionId}/records`

한 회차에서 여러 수강생의 출석·과제 기록을 한 번에 수정합니다. 한 명의 기록만 수정할 때도 이 API에 항목 하나를 보내면 됩니다.

와장과 그 회차가 속한 세미나의 담당 운영진만 수정할 수 있습니다. 다른 세미나 운영진이나 루키가 요청하면 `403`입니다.

**요청**

```json
{
  "records": [
    {
      "enrollmentId": 10,
      "attendance": "PRESENT",
      "assignmentStatus": "PASSED"
    },
    {
      "enrollmentId": 11,
      "attendance": "ABSENT"
    }
  ]
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `records` | array | ✓ | `null` 불가. 항목이 한 개 이상 있어야 함 |
| `records[].enrollmentId` | integer | ✓ | 양의 정수. 이 회차와 같은 세미나의 수강 신청 ID |
| `records[].attendance` | string \| null | | `PRESENT`, `ABSENT` 또는 `null` |
| `records[].assignmentStatus` | string \| null | | `PASSED`, `SUBMITTED_BUT_FAILED`, `NOT_SUBMITTED` 또는 `null` |

**부분 수정과 기록 삭제**

- 각 항목에는 `attendance`와 `assignmentStatus` 중 적어도 하나가 있어야 합니다. `enrollmentId`만 보낼 수는 없습니다.
- **프로퍼티를 생략하면 기존 값 유지, 명시적인 `null`이면 해당 기록 삭제**입니다.
- 해당 회차·수강생의 기록이 처음이면 보낸 값을 저장합니다. 생략한 필드는 미기록(`null`)으로 남습니다.
- 기존 기록이 있으면 보낸 필드만 수정합니다. 같은 회차·수강생의 출석과 과제 상태는 각각 하나만 존재해야 합니다.
- 이미 미기록인 필드에 `null`을 보내거나 기존과 같은 값을 보내는 것도 정상 요청입니다.
- 요청에 포함하지 않은 수강생과 다른 회차의 기록은 유지합니다.
- Grace Day와 탈락 여부는 변경하지 않습니다.

예를 들어 다음 요청은 출석을 유지하면서 과제 기록만 지웁니다.

```json
{
  "records": [
    {
      "enrollmentId": 10,
      "assignmentStatus": null
    }
  ]
}
```

**요청 전체의 원자성**

이 API의 한 요청은 하나의 비즈니스 작업입니다. 여러 행이나 테이블을 수정하더라도 **모두 성공하거나 모두 실패**해야 합니다.

예를 들어 10번 수강생의 출석을 수정하고, 11번 수강생의 과제 기록을 수정하던 중 실패했다면 10번의 변경도 남아서는 안 됩니다. 형식 오류, 없는 수강 신청, 처리 중 예외 등으로 요청이 실패하면 원래 상태를 유지해야 합니다.

요청 배열의 저장 순서는 정하지 않습니다. 모든 항목을 먼저 검증한 뒤 저장하는 것도 가능합니다. 다만 저장을 시작한 뒤 발생한 예외에도 전체 변경을 되돌릴 수 있어야 하며, 이를 팀 자체 롤백 테스트로 확인합니다.

**응답** — `204 No Content`

응답 body는 없습니다. 변경된 결과는 대시보드에서 확인할 수 있습니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `records`가 없거나 `null`, 빈 배열, 배열이 아닌 값임 | 400 |
| 배열의 항목이 `null`이거나 객체가 아님 | 400 |
| `enrollmentId`가 없거나 `null`, 양의 정수가 아닌 값임 | 400 |
| 한 요청에 같은 `enrollmentId`가 두 번 이상 나옴 | 400 |
| 항목에 수정할 필드가 없음 | 400 |
| 출석 또는 과제 상태가 허용된 값이나 `null`이 아님 | 400 |
| 없는 회차 또는 없는 수강 신청 | 404 |
| 수강 신청이 회차와 다른 세미나에 속함 | 404 |

여러 항목 중 하나에만 오류가 있어도 전체 요청이 실패합니다. 일부만 반영한 뒤 성공 응답을 보내거나, 항목마다 성공·실패를 나누어 응답하지 않습니다.

## 4. 팀 자체 테스트와 설계 문서

### 두 종류의 테스트

이번 주에는 운영진의 공개 테스트와 팀이 직접 작성하는 테스트를 함께 사용합니다.

| 구분 | 운영진 공개 테스트 | 팀 자체 테스트 |
| --- | --- | --- |
| 관점 | 공통 API 계약 | 팀이 선택한 구조와 구현 |
| 호출 방식 | HTTP 요청과 응답을 통해 확인. 현재 공통부는 MockMvc 사용 | API 또는 실제 Spring Service 호출과 DB 상태 확인 |
| 주요 대상 | 상태 코드, 응답 JSON, 동시 요청 후 최종 결과, 일괄 요청의 전체 반영 여부 | 실제 락·트랜잭션 경계, 저장 도중 예외가 발생했을 때의 롤백 |
| 실행 환경 | 운영진 원본 테스트와 팀의 `src/main`을 결합 | 팀 저장소의 테스트와 실제 MySQL |

팀 자체 테스트는 `src/test` 아래에 추가합니다. 운영진 테스트와 이름이 겹치지 않도록 별도 패키지나 클래스 이름을 사용하세요. 기존 공개 테스트를 삭제하거나 기대값을 바꾸어 통과시키지 않습니다.

### 직접 작성할 필수 테스트

실제 MySQL과 연결한 통합 테스트로 다음 다섯 시나리오를 작성합니다. 기존 `ApiIntegrationTest`를 상속해 도우미를 사용하거나, 팀 구조에 맞는 테스트 공통부를 만들어도 됩니다.

| 시나리오 | 준비와 실행 | 반드시 확인할 결과 |
| --- | --- | --- |
| 정원 경쟁 | 신청 기간 안인 정원 30명의 빈 세미나에, 서로 다른 승인 루키 100명이 한 번씩 동시 신청 | 성공 30건, 정원 마감 70건, 실제 수강 신청 30개 |
| 중복 신청 | 자리가 있는 세미나에 한 루키가 20회 동시 신청 | 성공 1건, 중복 충돌 19건, 해당 루키의 신청 1개 |
| 중복 취소 | 신청 기간 안에 한 루키가 자신의 기존 신청을 10회 동시 취소 | 성공 1건, 나머지는 신청 없음, 실제 인원은 한 번만 감소 |
| 신청·취소 혼합 | 정원 5명이 찬 세미나에서 기존 수강생의 취소와 신규 신청을 동시 실행 | 인원 보존식과 정원 제한 만족. 이후 빈자리를 채울 수 있음 |
| 저장 도중 롤백 | 일괄 기록 수정에서 실제 첫 DB 쓰기 뒤 예외 발생 | 호출 실패 후에도 모든 대상의 기록이 작업 전 상태와 같음 |

API를 호출하는 테스트에서는 각 시나리오의 상태 코드도 확인합니다. Service를 직접 호출하는 테스트에서는 성공과 예상한 업무 예외를 구분합니다. 관계없는 예외를 정상적인 정원 마감이나 중복 실패로 세면 안 됩니다.

회귀 확인을 위해 기록의 최초 저장·재수정·삭제, 잘못된 항목이 섞인 일괄 요청, Grace Day 경계값, 권한, 취소 후 재신청과 기록 초기화도 함께 테스트하는 것을 권합니다.

### 동시성 테스트 작성 시 확인할 점

- 사용자 생성, 가입 승인, 로그인, 세미나 준비는 요청을 동시에 실행하는 구간 전에 끝냅니다. 준비 데이터는 작업 스레드에서 조회할 수 있도록 커밋되어 있어야 합니다.
- `ExecutorService`와 `CountDownLatch` 등으로 여러 요청이 겹쳐 실행되게 합니다. 요청을 순서대로 반복 호출하는 것은 동시성 테스트가 아닙니다.
- 작업 100개를 스레드 32개의 풀에 제출하면 동시에 실행되는 작업은 최대 32개입니다. 시작 전 준비 완료를 기다린다면, 대기할 개수도 실제 실행 가능한 작업 수에 맞춥니다. 100개가 모두 준비될 때까지 기다리면서 32개가 스레드를 점유하게 만들면 진행할 수 없습니다.
- 모든 작업의 결과를 수집합니다. 작업 스레드의 예외가 메인 테스트에 전달되도록 `Future.get()` 등을 사용하세요.
- 예상한 정원 마감과 중복 충돌만 해당 실패로 집계합니다. 예상하지 못한 예외, `5xx`, 연결 실패, 타임아웃은 테스트 실패입니다.
- 시작 대기와 작업 완료 대기에 제한 시간을 두고, 실패하더라도 실행기를 종료합니다.
- 테스트를 바깥 트랜잭션 하나로 묶어 서비스의 트랜잭션 경계를 대신하지 않도록 합니다. 작업이 끝난 뒤 새로운 트랜잭션에서 최종 DB 상태를 확인합니다.
- 테스트마다 새로운 세미나와 사용자를 준비하여 실행 순서나 다른 테스트의 데이터에 의존하지 않게 합니다.
- 성공할 때까지 테스트를 반복하거나, 동작을 맞추기 위해 임의의 `sleep`에 의존하지 않습니다.

성공 응답 수뿐 아니라 실제 수강 신청 수와 중복 여부도 확인해주세요. 인원 집계 컬럼을 저장한다면 그 값과 원본 수강 신청 수가 같은지도 확인합니다. 공개 테스트에서는 특정 테이블 이름을 가정하지 않고 API 조회 결과를 비교합니다.

### 실제 DB 쓰기 이후의 롤백 검증

잘못된 일괄 요청을 보낸 뒤 데이터가 그대로인 것만으로는 롤백을 검증했다고 볼 수 없습니다. 모든 입력을 저장 전에 검증했다면 DB 쓰기가 한 번도 실행되지 않았을 수 있기 때문입니다.

팀 자체 롤백 테스트는 다음 순서로 작성합니다.

1. 변경 전 기록을 실제 MySQL에 저장하고 커밋합니다. 테스트에서 수정하려는 값은 기존 값과 다르게 준비합니다.
2. Spring에서 주입받은 실제 Service를 통해 일괄 수정 작업을 시작합니다.
3. 첫 번째 실제 DB 쓰기가 실행된 뒤, 다음 처리에서 예외를 발생시킵니다. 테스트용 저장 계층 래퍼 등 팀 구조에 맞는 방법으로 실패를 주입할 수 있습니다.
4. 예외가 호출자에게 전달되었는지 확인합니다.
5. 실패한 호출의 트랜잭션이 끝난 뒤 별도 트랜잭션에서 조회하여, 생성·수정·삭제한 내용이 모두 작업 전 상태로 돌아왔는지 확인합니다.

첫 쓰기가 실제로 실행되었다는 증거도 테스트에 포함하세요. 저장소 전체를 가짜 객체로 바꾸고 호출 횟수만 확인하는 테스트는 실제 DB 롤백 검증을 대신할 수 없습니다.

실패 주입은 테스트 코드에서 구성합니다. 이 테스트를 위해 운영 API에 강제 실패 파라미터나 별도의 테스트용 엔드포인트를 추가할 필요는 없습니다.

Spring의 기본 롤백 규칙을 사용할 때는 예외 타입도 확인하세요. 기본적으로 `RuntimeException`과 `Error`가 롤백 대상이며, Kotlin에서도 단순히 `Exception`을 상속했다는 이유만으로 자동 롤백되는 것은 아닙니다. 필요한 경우 업무 예외의 상속 관계나 `rollbackFor`를 명시합니다.

### 설계 문서

팀 `README.md`에 4주차 설명을 추가하거나 `docs` 아래에 별도 문서를 만들고 README에서 연결합니다. 다음 내용을 포함해주세요.

1. **어떤 문제가 있었는가?** 정원 초과나 중복 요청이 가능한 실행 순서를 설명합니다. 수정 전 문제를 재현했다면 테스트 결과도 함께 적습니다.
2. **왜 발생했는가?** 조회와 저장 사이의 경쟁 상태, 트랜잭션만으로 해결되지 않는 이유를 설명합니다.
3. **어떤 방법으로 해결했는가?** 락·제약조건·재시도·조건부 갱신 중 사용한 방법과 적용 범위를 설명합니다.
4. **왜 그 방법을 선택했는가?** 다른 방법과 비교한 장단점, 대기·재시도·추가 컬럼 관리 등 팀이 고려한 점을 적습니다.
5. **트랜잭션 경계는 어디인가?** 일괄 기록 수정과 수강 취소에서 함께 성공하거나 실패해야 하는 DB 변경을 나열합니다.
6. **어떻게 검증했는가?** 자체 테스트 위치와 실행 방법, 동시성 결과, 첫 DB 쓰기 이후 실패를 주입한 방법과 롤백 검증 결과를 적습니다.

Migration이 추가되었다면 변경한 스키마와 기존 데이터를 유지하는 방법도 함께 설명합니다.

## 5. 코드 리뷰와 머지

2·3주차와 같습니다. PR은 팀원 **한 명 이상**의 review와 approve를 받은 뒤 `main`에 머지합니다. 특별한 경우가 아니라면 로컬에서 `main`으로 직접 push하지 않습니다❗❗

모든 팀원이 적어도 하나 이상의 커밋으로 기여해야 합니다. 기능과 테스트를 함께 작성하고, 리뷰할 때 다음 내용도 확인해주세요.

- 동시 요청의 성공·실패 건수와 최종 데이터가 요구사항에 맞는가?
- 예상하지 못한 예외가 정상적인 충돌로 처리되거나 테스트에서 누락되지 않는가?
- 일괄 수정과 취소 중 실패했을 때 부분 반영이 남지 않는가?
- 실제 DB 쓰기 이후의 롤백 테스트가 있는가?
- 생략과 `null`, 미기록과 결석·미제출을 구분하는가?
- 다른 세미나의 수강 신청을 수정하지 못하며, 기존 인증·인가와 API가 유지되는가?

팀 자체 테스트를 추가한 PR에는 실행 명령과 결과를 남기고, 설계 문서로 연결해주세요.

## 6. 채점 확인

### 로컬 확인

Docker를 켠 상태에서 다음 명령으로 공개 테스트와 팀 자체 테스트를 실행합니다.

```bash
./gradlew test
```

Windows PowerShell에서는 `./gradlew.bat test`를 사용합니다. 로컬 보고서는 `build/reports/tests/test/index.html`에서 확인할 수 있습니다.

운영진이 테스트를 추가하거나 수정했다고 공지하면 원본 업데이트를 반영한 뒤 다시 실행해주세요.

### 자동 채점과 팀 자체 테스트

Fork 저장소의 `main`에 push하면 GitHub Actions가 채점 서버에서 운영진 원본 테스트를 실행합니다. 결과는 [리더보드](https://spring-seminar-judge.vercel.app/)에서 확인합니다. 제출과 로그 확인 방법은 [README](../README.md)를 참고하세요.

기존과 마찬가지로 채점 서버는 팀의 **`src/main`만** 가져가고, 테스트와 빌드 설정은 운영진 원본을 사용합니다.

| 항목 | 확인 방법 |
| --- | --- |
| 기존 API와 새 API의 계약, 동시 요청 후 결과, 일괄 요청의 전체 반영 여부 | 운영진 공개 테스트와 자동 채점 |
| 실제 쓰기 이후의 롤백 검증, 팀 자체 테스트의 내용과 결과 | 팀 저장소의 테스트와 PR 리뷰 |
| 동시성 제어 방식, 트랜잭션 경계, 선택 이유 | README 또는 연결된 설계 문서와 PR 리뷰 |

- 팀이 작성한 Migration과 애플리케이션 설정은 `src/main/resources`에 포함되므로 자동 채점에 반영됩니다.
- 팀 자체 테스트를 삭제하거나 기대값을 바꾸어도 운영진의 자동 채점 결과는 달라지지 않습니다.
- 팀의 `src/test`와 README는 현재 자동 채점에 포함되지 않습니다. **리더보드 통과만으로 자체 테스트와 문서 작성 조건까지 충족되는 것은 아닙니다.**
- 제출 전 기존 기능과 새 기능, 팀 자체 테스트를 모두 실행하고 PR 리뷰까지 마무리해주세요.
