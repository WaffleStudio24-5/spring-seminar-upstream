# 🤦 개인 과제: nginx 로드 밸런싱

세미나 실습에서는 OCI 인스턴스에 nginx를 설치하고, `/api/`로 오는 요청을 `app.py` 서버 한 대로 넘기는 리버스 프록시를 구성했습니다. 개인 과제는 해당 인스턴스에서 각자 진행합니다.

`app.py` 서버를 세 대로 늘리고, nginx가 요청을 세 서버에 **라운드 로빈**으로 나누어 보내도록 설정합니다.

```text
                         ┌─> app.py (127.0.0.1:8080)
요청 ──> nginx (80) ──────┼─> app.py (127.0.0.1:8081)
                         └─> app.py (127.0.0.1:8082)
```

## 0. 실습 내용 확인

실습을 마친 상태라면 인스턴스에 다음이 준비되어 있습니다. 빠진 것이 있다면 실습 자료를 따라 먼저 마쳐주세요.

- nginx가 설치되어 있습니다.
- OCI Security List와 인스턴스의 `iptables`에서 80 포트가 열려 있습니다.
- 홈 디렉터리에 `app.py`가 있습니다.
- `/etc/nginx/sites-available/default`의 `server` 블록 안에 `location /api/` 블록이 있습니다.


## 1. 서버 세 대 실행하기


```bash
pkill -f app.py

python3 app.py 8080 &
python3 app.py 8081 &
python3 app.py 8082 &
```


## 2. nginx 설정 수정하기


```bash
sudo nano /etc/nginx/sites-available/default
```

**두 곳**을 수정합니다.

### ① upstream 블록 추가

파일의 맨 위, server { 블록 바깥에 다음을 추가합니다.

```nginx
upstream backend {
    zone backend 64k;
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}
```

- `upstream`은 요청을 나누어 받을 서버 묶음에 이름(`backend`)을 붙입니다. 분배 방식을 따로 적지 않으면 라운드 로빈입니다.
- `zone`은 nginx의 여러 워커 프로세스가 "다음 차례가 누구인지"를 공유하게 합니다. 없으면 워커마다 따로 순서를 세어, 차례대로 응답하지 않는 것처럼 보일 수 있습니다.

### ② `proxy_pass` 대상 변경

실습에서 `server` 블록 안에 추가한 `location /api/` 블록에서 `proxy_pass` 한 줄만 바꿉니다.

```nginx
location /api/ {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

서버 한 대의 주소(`http://127.0.0.1:8080`) 대신 ①에서 만든 묶음의 이름을 적습니다.

### 적용

문법을 확인하고 nginx에 반영합니다.

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 2. CORS 설정

브라우저는 한 출처(프로토콜 + 호스트 + 포트)의 페이지가 **다른 출처**의 서버로 요청을 보내는 것을 기본적으로 막습니다. 팀 프론트와 팀 서버는 호스트가 달라 서로 다른 출처입니다. 서버가 응답 헤더로 "이 출처의 요청은 받는다"고 알려 주어야 브라우저가 요청을 허용하며, 이 약속을 CORS라고 합니다.

- 브라우저는 실제 요청 전에 `OPTIONS` 메서드의 **사전 요청(preflight)** 으로 허용 여부를 먼저 묻습니다. 사전 요청에는 토큰이 실리지 않습니다.

팀 서버가 다음을 만족하도록 설정합니다.

- 허용할 출처를 `waggle.cors.allowed-origins` 프로퍼티에서 읽습니다. 배포 환경에서는 환경 변수 `WAGGLE_CORS_ALLOWED_ORIGINS`로 값이 들어옵니다.
- 그 출처에서 오는 `GET`, `POST`, `PATCH`, `DELETE`, `OPTIONS` 요청과 `Authorization`, `Content-Type` 헤더를 허용합니다.
- 사전 요청(`OPTIONS`)은 **로그인 여부를 검사하지 않고 허용**해야 합니다. 토큰이 없다는 이유로 `401`을 응답하면 브라우저가 실제 요청을 보내지 않아, 로그인한 사용자의 요청도 모두 실패합니다.
- 프로퍼티 값이 없어도 서버가 실행되어야 합니다. 로컬 실행과 테스트에는 이 환경 변수가 없습니다.

## 2-2. 남은 엔드포인트 구현

Waggle의 마지막 세 기능을 구현합니다. 세 엔드포인트 모두 로그인이 필요하고, 에러 응답은 기존 `ApiErrorResponse` 형식입니다.


| 기능 | 메서드와 경로 | 성공 |
| --- | --- | --- |
| [내 정보 수정](#patch-usersme) | `PATCH /users/me` | `200 OK` |
| [회원 탈퇴](#delete-usersme) | `DELETE /users/me` | `204 No Content` |
| [회차 삭제](#delete-sessionssessionid) | `DELETE /sessions/{sessionId}` | `204 No Content` |

### `PATCH /users/me`

자신의 이름과 GitHub 사용자명을 수정합니다.  로그인한 사용자 누구나 호출할 수 있습니다.

```json
{
  "name": "김와플",
  "githubUsername": "waffle-kim"
}
```

- 두 항목 모두 선택입니다. **보낸 항목만 수정**하고, 보내지 않은 항목은 유지합니다.
- 응답은 `GET /users/me`와 같은 형식의 수정된 사용자 정보입니다.

| 상황 | 응답 |
| --- | --- |
| `name` 또는 `githubUsername`이 빈 문자열이거나 공백뿐임 | 400 |

### `DELETE /users/me`

서비스에서 탈퇴합니다. 운영진과 루키가 호출할 수 있습니다.

- 사용자를 삭제하지 않고 가입 상태를 `WITHDRAWN`으로 바꿉니다.
- 신청 기간이 진행 중인 세미나의 수강 신청은 출석·과제 기록과 함께 취소합니다. 자리가 비므로 다른 루키가 신청할 수 있습니다.
- 신청 기간이 끝난 세미나의 수강 신청과 기록은 그대로 둡니다. 대시보드에도 계속 나옵니다.
- 상태 변경과 수강 신청 취소는 전부 반영되거나 전부 반영되지 않아야 합니다.

탈퇴한 뒤에는 다음과 같이 동작합니다.

- 같은 이메일과 비밀번호로 로그인하면 `401`입니다.
- `GET /users` 목록에 나오지 않습니다.
- 같은 이메일로 다시 가입할 수 없습니다(`409`).

| 상황 | 응답 |
| --- | --- |
| 와장이 탈퇴를 요청함 | 409 |

### `DELETE /sessions/{sessionId}`

수업 회차를 삭제합니다. 와장과 그 회차가 속한 세미나의 담당 운영진만 삭제할 수 있습니다.

- **마지막 회차**만 삭제할 수 있습니다. 마지막 회차는 `startsAt` 오름차순, 같은 시각이면 회차 ID 오름차순으로 정렬했을 때 맨 끝의 회차입니다.
- 그 회차에 출석 또는 과제 기록이 하나라도 있으면 삭제할 수 없습니다.

| 상황 | 응답 |
| --- | --- |
| 다른 세미나의 운영진 또는 루키가 요청함 | 403 |
| 없는 회차 | 404 |
| 마지막 회차가 아님 | 409 |
| 출석·과제 기록이 있음 | 409 |
